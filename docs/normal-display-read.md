# 通常表示と変更前の安全確認の分離

基準コミット`7aa14579d171651d37444ddd9a456cbb6450b9ac`からの安定化変更。実装当時は未コミットで実機確認を待ち、今回ユーザーから下記4項目の成功報告を受けた。最新の検証・残課題は[安定化作業の到達点](stabilization-status.md)を参照。応答停止の根本原因を完全に特定したとは扱わない。

## 背景

通常UIのログ`mvusvtuijciw1`では、一覧＋アクティブ取得のsyncは31回すべて完了したが、総シート数のsyncは29回開始・28回終了。最後の`api.sync.total`は少なくとも254.542秒未完了だった。以前は分離されていたactive取得のsyncで停止しており、どちらも同一取得内の2回目のsync。ホスト内部の原因は未特定。

## 取得情報の役割

| 情報 | 通常表示 | 移動直前・移動後 |
|---|---|---|
| シートID・名前・位置・表示状態 | 一覧、検索、切替、ドラッグの移動要求作成 | 対象・順序・状態の照合 |
| アクティブID | アクティブ表示 | 不明時拒否、移動後の維持を確認 |
| ブック名・URL | 既存のブック変化検知・世代管理 | 別ブックへの操作を防ぐ照合。恒久IDとは扱わない |
| 読み取り専用・構成保護・シート保護 | 既知の操作不可状態を画面で抑止。同一syncで取得 | 再取得し必ず確認 |
| `workbook.functions.sheets()`による総シート数 | **取得しない。未確認のnullを維持** | **必ず取得。通常シート数との不一致・不明は書き込み禁止** |

通常表示は`readWorkbookState` → `loadDisplayState` → 1回の`context.sync()`。初回表示・イベント更新・手動更新・切替後の表示再取得に適用する。保護情報は既存の表示上の抑止と差分照合に使い、追加のsyncなしで残す。

厳密な取得は従来の`loadWorkbookState`を維持し、メタデータ＋activeのsyncと総数のsyncを実行する。移動前後・失敗後の再取得から呼ぶ。PoCとA/B/C独立比較のコード・挙動は今回変更しない。

`readWorkbookState`は既存の呼出名を維持した通常表示用ラッパーであり、これを変更許可の根拠にしてはならない。

## ドラッグと変更許可の区別

表示スナップショットは`readPurpose: "display"`、`totalSheets: null`を持つ。安全確認済みとは扱わず、既存の厳密な`moveRestriction`では引き続き拒否される。

UIでは`dragRestriction`を使い、名前検索を含むドラッグによる移動要求を作成できる。これはExcelへ位置変更を送ってよいという許可ではない。既に取得済みのreadonly・構成保護・対象保護・位置欠番・active不明などは引き続き抑止する。

ドロップ後は同じ共通APIキュー内で以下を実施する。

1. `loadWorkbookState`で総シート数を含めて厳密に再取得する。
2. 総数不明・不一致、未対応シート混在、readonly・構成保護・対象保護などを拒否する。
3. ドラッグ開始時に観測したブック・ID・名前・位置・表示状態・保護状態を照合する。表示用baselineの総数は未取得なので比較対象にせず、代わりに手順2の現在状態で厳密に判定する。既存の安全確認用baselineは従来どおり総数も照合する。
4. 世代・対象の検証を通った場合だけ位置を書き込む。
5. 移動後も総数と状態を再取得し、期待順序・状態・アクティブ維持を確認する。失敗時の再取得と結果不明の表示も維持する。

グラフシートが一覧の末尾以降にあり表示情報だけでは混在を識別できない場合、ドラッグの開始自体は可能でも、ドロップ後の総数照合で変更を拒否する。シート一覧の件数をブックの全シート数と推定しない。操作開始のUI判定と、実際の書き込みの許可を分離した変更である。

総数の安全確認を試みて失敗した結果（表示用フラグなし）を、単なる未取得の表示結果と混同しない。古い総数のキャッシュを流用して変更を許可する処理は追加していない。

## 同期・エラー・診断

- 通常表示の成功は1run/1sync。イベント登録・再登録や、SheetDock自身のシート切替操作の確認は別の処理であり、ペイン全体のAPI回数が常に1回という意味ではない。
- 通常の診断段階は`api.run.read`内の`api.sync.displayMetadataActive.start/end`。通常表示だけなら`api.sync.total.start`は出ない。
- 表示の統合バッチがエラーで終了した場合だけ、新Contextで一覧のみの退避を1回行う。`api.sync.displayMetadataOnly`を記録し、active不明の警告とドラッグ禁止を維持する。退避も総数を取得しない。
- 厳密な安全確認は従来の`api.sync.metadataActive`と`api.sync.total`。通常の移動操作でこれらが出るのは想定どおり。
- 未応答中は退避や別取得を始めない。共通キューの直列化、15秒監視、世代による古い結果の破棄は維持する。
- エラーを返すことと未応答は区別する。例外時にもendが出るため、errorと合わせて読む。

## Excel for the webでの最小確認

1. 既存の開発サーバーを起動し、古い未完了APIを持ち越さないようExcelのブラウザータブ全体を再読み込みする。比較モードなら「通常画面へ（再読み込み）」で戻る。通常UIで、PoCイベント観測はOFF。
2. 検証ブックで一覧・アクティブ表示を確認。Excel標準UIで切替・並び替えを行い追従することを確認する。
3. 名前編集を開始して約2秒後にEsc。停止しなければ名前変更を確定する操作を5〜10回行う。最終名とアクティブ状態へ追いつくか確認する。
4. 通常UIから単一シートを移動し、Excelと同じ順序になるか確認。続けて検索中の単一移動も確認する。安全確認を待つ時間は発生し得る。
5. 既存の構成保護やグラフシート混在の専用検証ブックがあれば、変更が拒否されることを確認する。通常ブックを危険な状態へ変更して試す必要はない。

停止した場合は追加操作を止め、通常UIの診断を保存する。DevToolsのlocalhost:3000フレームで次を実行する（PowerShellではない）。

```javascript
copy(JSON.stringify(window.sheetDockDiagnostics.snapshot(), null, 2))
```

保存内容とともに「Excel標準UIでの編集か、SheetDockからの移動か」「最後の開始段階」を報告する。通常表示中に`api.sync.total`が出る場合は、古い配信コード・別の移動操作・PoC観測が混ざっていないかを確認する。閉じる前後を比較するなら両方の診断sessionを保存する。

## 自動検証

全300テスト／24ファイルが成功。作業開始時の279件を保持し、21件追加した。

- 通常表示が1syncで完了し、SHEETSを呼ばないこと。退避も総数を取得しないこと。
- 表示結果の総数nullを安全確認済みと扱わないこと。
- 表示baselineでも総数不明・不一致、保護、名前・順序・表示状態・保護状態変更で書き込みを拒否すること。
- 移動前後に厳密な取得を通すこと、移動後の確認失敗を成功としないこと。
- 実際の取得／移動／共通キューを通す結合テストで、総数確認未応答中は書き込みと後続取得を開始しないこと。
- 通常UIの検索条件維持と、移動の安全確認失敗の表示。

TypeScript型チェック、Development／Productionビルド、マニフェスト検証が成功。両ビルドともエラー0・警告0。webpack統計でProductionの`src/dev`／`src/poc`モジュールが0件、Developmentでそれぞれ7件／8件であることを確認した。`git diff --check`も成功。

## 追加の実機結果（2026-10-30記録）

ユーザーによるExcel for the webの報告：

- 名前編集開始 → 約2秒後にEscでキャンセル：正常。
- 名前変更を5〜10回繰り返す：正常。

今回の再現手順では、従来のOffice.js API応答停止は発生しなかった。根本原因の特定、1sync化だけの因果効果、他条件での再発防止は未証明。移動の異常系やPoC、独立比較まで検証済みへ変更しない。

## 残るリスク

1回のsyncでもOffice.jsが応答しなくなる可能性は残る。移動の厳密な検証には総数評価を残すため、そこで停止すれば変更を送らず待機する。書き込み後の確認が止まった場合は、変更が適用済みの可能性を成功と誤認しないことが必要。

共同編集・Excel標準UIとの完全な排他や原子的操作は保証しない。取得・確認後に変化する競合への既存の検証と制約は維持する。
