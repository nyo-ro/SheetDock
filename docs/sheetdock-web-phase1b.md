## 3. API対応と自動同期

| 対象 | API | 正式ExcelApi Set | 今回の対応 | 実機 |
|---|---|---|---|---|
| アクティブ化 | WorksheetCollection.onActivated | 1.7 | コレクションに1回登録、イベントログと再取得 | 未検証 |
| 追加 | onAdded | 1.7 | 同上。新シートごとの登録は不要 | 未検証 |
| 削除 | onDeleted | 1.7 | 同上 | 未検証 |
| 名前 | onNameChanged | 1.17 | 同上 | 未検証 |
| 位置 | onMoved | 1.17 | 同上。直接移動のみ。追加等の間接変化はAdded/Deletedでも再取得 | 未検証 |
| 表示状態 | onVisibilityChanged | 1.17 | 同上 | 未検証 |
| シート保護 | onProtectionChanged | 1.14 | 同上。ブック構成保護とは別 | 未検証 |
| ブック構成保護 | Workbook.protection.protected | 1.7 | 今回の正式APIに専用変更イベントを確認できず、再取得で判定 | 未検証 |
| 読み取り専用 | Workbook.readOnly | 1.8 | 操作直前に取得して拒否 | 未検証 |

すべて正式公開APIを使用する。マニフェストの最低ExcelApi 1.17は維持。登録時にも各Requirement Setを確認する。

イベントコールバックは履歴追加と更新予約のみ。150msの窓で集約し、取得中の追加要求は次の1回へ持ち越す。1回の観測は全通常ワークシートのメタデータ取得とアクティブ取得を分けた2 sync。セルデータは読まない。失敗後に自動無限再試行はせず、次イベント・手動・フォーカス復帰で再試行する。大量シートでの性能と150msの適切さは実機未評価。

手動更新・基本の切替・PoCの再取得/変更を同一のPromiseキューで直列化。操作途中のイベント取得は変更処理の後へ回る。読み取り結果は基本一覧へ反映する。手動更新は残す。

登録/解除要求も直列化し、同時ONでも登録1回。解除は登録したRequestContextを使う。登録または解除に失敗したら状態不明とし、ペイン再読み込みまで再登録を禁止。Reactの終了時に解除を試行する。Officeによるペイン終了・再読み込み時のイベント寿命は公式仕様に依存し、閉じて再表示したときの実挙動はチェックリストで確認する。終了時に解除できない通信断も完全復旧保証はしない。

自動同期ON中はブラウザー/ペインのフォーカス・visibility復帰も再取得の契機にする。イベントがない/届かない変更を即座にすべて検知する保証はない。特に共同編集のイベント到達・順序・欠落は未検証。

## 4. Hidden／VeryHidden

| 操作 | 試作 | 状態の確認方法 | 実機判定 |
|---|---|---|---|
| Visible→Hidden | visibilityを設定 | before/after、activeId、元の他属性を再取得 | 未検証 |
| Visible→VeryHidden | 同上 | 同上 | 未検証 |
| Hidden→Visible | 同上 | 同上 | 未検証 |
| VeryHidden→Visible | 同上 | 同上 | 未検証 |
| VeryHidden→Hidden | 同上 | 同上 | 未検証 |
| Hidden複製 | copy("After", source)を直接呼ぶ | 元の表示状態不変、新ID1件、挿入位置、複製先visibilityを観測 | 未検証 |
| VeryHidden複製 | 同上。失敗しても自動で元を再表示しない | 複製先の表示状態を推測しない | 未検証 |
| Hidden削除 | delete() | 対象消失、残りの順序と属性を再取得 | 未検証 |
| VeryHidden直接削除 | ガードで拒否 | 公式仕様のInvalidOperationを避ける | 実機では呼んでいない |
| VeryHidden削除実験 | Hiddenへ変更→確認→delete | 各段階を記録。失敗時は限定条件で復元試行 | **復元保証不可。本番採用不可** |
| 非表示シート移動 | positionを設定 | 表示状態を変えず順序を確認 | 未検証 |

visibilityの読み取りは1.1、設定は1.2、copyは1.7、deleteは1.1。VeryHiddenの直接削除は公式にInvalidOperationと明記され、先にHiddenまたはVisibleへの変更が必要。本PoCではHiddenを選ぶため、一時的に表示する処理はない。

VeryHidden復元は、一時変更が成功したと確認でき、削除失敗後にも対象のID・名前・順序・表示/保護状態と全体構成が一致するときだけ試す。復元APIの失敗、観測不能、競合時は`recovery.status: unknown`。成功確認前に通信断した場合も復元を決めつけない。削除後に対象が消失していれば復元不要だが、元のステップの状態不明判定は成功に書き換えない。

最後のVisible通常ワークシートを非表示/削除する操作は送信前に拒否する。独立グラフシートまで含む「最後の表示シート」を証明するものではない。

## 5. 並び替え

`Worksheet.position`（1.1）は0基準のブック内位置。UIでは元一覧の挿入境界（0～件数）を指定する。5件なら0が先頭、5が末尾で、最終positionを直接入力する仕様ではない。

Sheasideの`WorksheetMoveRules.GroupOrder`を参照し、元順序の選択集合を一塊として挿入する。選択順の入力が逆でも元順序を維持する。非選択の相対順序も維持する。純粋関数は絞り込み一覧も扱い、絞り込み末尾は最後の表示対象の直後になる。今回のPoC UI自体は未絞り込みの全ワークシートを使う。

- 単一移動：必要な場合だけ1回のposition書き込み。同じ順序なら書き込み0回。
- 複数移動：選択シートだけを順に末尾へ集め、その後最終位置へ並べる。最大おおむね2×選択件数の書き込み。非選択シートにはpositionを直接設定しない。
- 途中順序も`orderAfter`として事前計算。各段階で、操作前の最新構成と直前の期待構成を照合し、操作後に実順序・属性を再取得する。
- 最終的な`expectedOrder`と`actualOrder`を比較し`orderMatches`を出す。
- 各段階は通常、事前観測2 sync＋書込1 sync＋事後観測2 sync。性能最適化より観測と安全側の中止を優先するPoC。多数選択の実用性は未評価。
- 原子的トランザクションではない。途中停止時はそこまでの移動が残り、自動ロールバックしない。

5シートの全非空部分集合31通り×境界6通り=186ケースについて、計画を逐次適用した最終順序・途中順序・相対順序・書込対象が選択内に限られることを自動検証した。実Excelでのposition挙動は未検証。

## 6. 独立グラフシート混在

Microsoftの通常Worksheet APIの説明は独立グラフシート/マクロシートを対象外としている。Worksheet.chartsは通常シート上の埋め込みグラフであり、独立グラフシート一覧の代わりにはならない。

本PoCの観測は通常シート情報とactive取得を分け、active取得失敗でも一覧・positionを保持する。全種別の総数・名前・表示状態は取得できると仮定しない。位置の欠番は混在の疑いになるが、欠番がないことは非混在の証明にならない（末尾の対象外シート等）。

| 検証項目 | 今回の扱い |
|---|---|
| 一覧・位置 | 観測できる。Excelの全タブと照合して欠落/欠番を手動記録 |
| アクティブ | IDまたはエラーを記録。対象外IDならactiveId=null |
| 名前重複 | 通常ワークシート内の大小文字不問一致だけを表示。一致なしでも名前の利用可能性は不明 |
| 並び替え・削除 | **混在/不明ブックでは変更を許可しない**。API実行結果は未検証 |
| 最後の表示シート | 全種別を把握できず保証不可。混在ブックは変更拒否 |
| グラフシートがアクティブ | 観測エラー/IDを残す。変更拒否。Web自体が編集不可ならその制約も記録 |

グラフシートの変換・削除・ワークシート化は行わない。独立グラフシート混在での変更APIそのものの挙動は、この安全側PoCでは結論を出せない。混在対応をv1.0.0に含めるなら、対象外シートを確実に把握する方法を別途検証する必要がある。

## 7. 保護・競合・途中失敗

- 操作前ごとに対象を含む通常シート一覧・ブック名・構成保護・readOnlyを再取得。名前・position・visibility・シート保護も比較する。
- IDはブック内の参照キーとして使うが永久的な実体識別子とみなさない。公式資料にはMacで削除後のID再利用可能性が記載されている。
- 全構成の変更を保守的に検出するため、対象外シートの追加等でも計画を作り直す。
- 構成保護・readOnlyは拒否。シート保護がある対象もPoCでは保守的に拒否する。シート保護がすべてのメタデータ操作をExcel自身で禁止する、と確認したわけではない。
- アクティブシートは変化を観測するが、構成競合fingerprintには含めない。名前・ID等が同じまま別実体へ置き換わる競合や、最終確認と書込の間の競合を完全には検出できない。
- 同じペイン内の順序制御は、他ペイン・Excel標準UI・共同編集の完全な排他ではない。

| 状態 | 意味 |
|---|---|
| success | APIが完了し、事後観測がその操作の期待と一致 |
| failed | 送信前の再検証/保護/合成エラーで中止。その段階の書込は送っていない |
| unprocessed | 前段階の中断により未実行 |
| unknown | APIへ送信後にエラー/観測失敗/期待不一致。実際に適用された可能性を残す |

コピーは追加ID1件と配置・元シート不変を確認する。複製先のvisibilityは観測対象としてそのまま残し、元と同じはずと断定しない。失敗時に作成された可能性のあるシートを自動削除する処理もない。

PoCの失敗注入は`SyntheticFailure`と表示される人工的な制御フロー試験で、実ExcelのAPIがそのエラーを返した証拠ではない。書込後の注入は実際に変更が適用された後に起きるため、必ず使い捨てブックで行う。処理中のペイン終了/再読み込みでも変更の取り消しは保証しない。

## 9. Web版Excelの実機チェックリスト

### 準備

1. OneDrive等に新規の使い捨てブック`SheetDock-PoC`を作り、通常シートA/B/C/D/Eをこの順で用意する。AをVisibleの基準シートとして残す。業務・個人ブックを使わない。破壊試験ごとにブックを作り直すか検証専用コピーを用意する。
2. 前回の開発用証明書設定済み環境でPowerShellを開き、以下を実行する。今回は証明書の再登録は行っていない。

```powershell
cd .\SheetDock  # Run from the parent of your checkout
$env:PATH = "$PWD\.local-tools\node-v24.22.1-win-x64;" + $env:PATH
npm.cmd run dev
```

3. 前回と同じmanifest.xmlをWeb版Excelへ読み込む。既に読み込み済みならペインを開き直し、必要ならExcelブラウザータブを再読み込みする。基本UIの下に「Office.js技術検証（開発専用）」が表示されることを確認。
4. 「観測・再取得」でname、ID、position、visibility、protected、activeId、readOnly、structureProtectedを確認する。
5. 変更試験の場合だけ2つのチェックを入れ、観測値のnameを確認用ブック名へ完全一致で入力する。対象IDは観測JSONからコピーする。シート名やpositionではなくIDを指定する。
6. 操作・境界・失敗注入（通常は0）を指定し「計画を作成」。計画はその後の再取得でも固定される。内容を見て「確認して実行」。確認ダイアログで取り消せば書き込まない。
7. 操作前後・結果・イベント履歴を手動コピーして、下記記録欄とともに報告する。ログはメモリー内だけで、ペイン再読込時には消える。

### A. 自動同期（すべて今回未検証）

| 手順 | 記録する観測 |
|---|---|
| 自動同期をON、OFF、ONにする | 1操作につき想定イベントが増え、登録回数に比例して重複しない |
| Excel標準タブでA→Bへ切替 | onActivated、基本一覧のアクティブ表示、取得回数 |
| Excel標準UIでシート追加・削除 | onAdded/onDeleted、件数・位置の再取得 |
| BをB2に名前変更 | onNameChangedと基本一覧の名前 |
| Cを標準UIで移動 | onMoved、位置。追加による間接移動は別に確認 |
| 標準UIでBをHidden→Visible | onVisibilityChanged、一覧。VeryHiddenは後述PoCで試す |
| 標準UIでシート保護ON/OFF | onProtectionChanged、protected |
| 素早く複数の変更を連続実行 | 履歴件数と取得回数、最終状態がExcelと一致すること。途中取得中の変更も含める |
| ペインを閉じ再表示 | 初回状態の再取得、必要に応じ再ON、重複履歴がないこと |
| タブを離れて戻る | ON時にフォーカス復帰で再取得されること |
| ネットワーク不調後に手動更新 | エラー、古い成功表示を残さないこと、復旧可否 |

同じ操作で複数種類のイベントが起きることと、同じハンドラの二重登録は区別する。UIの取得回数とイベントの種類/時刻を添えて記録する。

### B. Hidden/VeryHidden（すべて今回未検証）

Bを対象に、Visible→Hidden→Visible、Visible→VeryHidden→Visible、VeryHidden→Hiddenを1回ずつ計画・実行する。各回でvisibility、activeId、Excelタブ表示を照合する。Bをアクティブにした場合とAをアクティブにした場合を分ける。

B=Hiddenでcopy、B=VeryHiddenでcopyを実行し、元の状態、新しいID/名前/visibility/position、activeIdを記録する。APIが拒否した場合はそのままエラーを保存し、再表示して強行しない。

Hidden削除を試す。VeryHidden直接削除はPoCガードで送信前にfailedになることを確認。**VeryHidden削除実験は使い捨てコピーでのみ**実行し、成功時の2段階を記録する。失敗注入step=2/beforeで復元実験、step=1/afterで状態不明を確認する。復元がunknownなら元状態へ戻ったと考えず、観測し直して検証ブックを破棄する。

最後の表示シート試験では、通常シートのみの検証ブックでA以外をHiddenにし、AのHidden/VeryHidden/削除がfailedで送信されないことを確認。AのVisible維持とタブ表示を照合する。

### C. 並び替え（すべて今回未検証）

毎回A/B/C/D/Eの元順序へ戻した新規コピーで試す。IDはコピーごとに取り直す。

| 対象・境界 | 期待する最終順序 |
|---|---|
| E、0 | E A B C D |
| A、5 | B C D E A |
| D、1 | A D B C E |
| B、4 | A C D B E |
| B、1または2 | A B C D E（書込0） |
| B,C、0 | B C A D E |
| B,D、5 | A C E B D |
| B,D、0 | B D A C E |
| B,C、2 | A B C D E（書込0） |

BをHidden、DをVeryHiddenにした状態でも上記複数移動を行い、visibilityが変わらず`orderMatches=true`となるか確認。非選択・選択内の相対順序と途中`orderAfter`を確認する。

2ステップ以上の計画で失敗注入step=2/beforeを指定し、1段階目success、2段階目failed、残りunprocessedになること、実順序が途中状態で残ることを確認。afterの場合はその段階がunknownとなり、変更適用済みの可能性を記録する。
